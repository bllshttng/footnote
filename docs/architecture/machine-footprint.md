# Machine footprint

`fno doctor footprint` is the read-only instrument for the fleet's total machine cost. It measures direct fno control-plane work plus the transitive descendants those workers launched.

The closure criterion is `fleet_cpu_cores` at or below one core and `direct_process_count` at or below live roster rows plus one daemon. `process_count` still reports the full attributed tree. Resident memory is reported for context. It is not part of the closure criterion.

The verb reads one file-backed `ps -Ao pid,ppid,etime,%cpu,rss,command` snapshot. It resolves each row's parent chain with a cycle-safe, memoized walk. A directly attributable row is a process whose executable is `fno`, `fno-py`, `fno-agents`, `fno-agents-daemon` or `fno-agents-worker`, including Python-launched `fno-py`. Every transitive descendant inherits attribution, so shells, `cargo`, `rustc`, `pytest` and future workload commands land in the fleet total. An unrelated tree with byte-identical commands remains outside the fleet.

The direct bucket is `sustained_cpu_cores`. A directly attributable process with `etime` below `SUSTAINED_FLOOR_SECONDS` (default 30 seconds) contributes to `transient_call_count`, `direct_process_count` and `process_count`, but not direct sustained CPU. The descendant bucket is `descendant_cpu_cores` and counts descendant CPU immediately, including short-lived build and test processes. `fleet_cpu_cores` is the sum of direct sustained and descendant CPU. `descendant_process_count` identifies how much of the process count came from launched work.

The observer process and its complete descendant subtree are excluded from CPU, process, RSS and top-consumer totals. Missing parents and ancestry cycles terminate safely without attributing a row unless the chain reaches a valid fno root. Each PID is counted at most once.

`--json` emits `sustained_cpu_cores`, `descendant_cpu_cores`, `fleet_cpu_cores`, `descendant_process_count`, `direct_process_count`, `process_count`, `rss_gb`, `cpu_capacity_cores`, `fleet_percent_capacity`, `fleet_percent_measured_cpu`, `load_1m`, `max_load_per_cpu`, `load_ceiling`, `load_cpu_count` and `spawn_load_status` with the thresholds and exit code. `fleet_percent_capacity` is fleet cores divided by constrained logical CPU capacity: the minimum of the affinity count, the host count and the cgroup quota. The spawn gates compute their load trigger and backstop from the affinity/parallelism count alone. On a quota-constrained host the footprint denominator can be smaller than the ceiling the refusing gate used. Those two numbers answer different questions, machine capacity against admission ceiling. The share comparison has no such gap, because both its terms come from this reading. The spawn-load fields come from the same effective CPU snapshot used by the Python admission gate. The report names the exact one-minute load, factor, CPU count and ceiling that decide the trigger. `fleet_percent_measured_cpu` is fleet CPU divided by total CPU in the non-observer rows of the snapshot. When live worker rows cannot be attributed to processes, `attribution_gap` names them. The fleet share above it is an undercount. A spawn gate reads a gapped share as unknown, never as headroom.

Human output prints `spawn load: <load> against <ceiling> (max_load_per_cpu <factor> x <cpus> cpus; <status>)` beside fleet CPU. When load is readable, `spawn_load_status` is `within` or `exceeded`. It is `disabled` or `unavailable` otherwise. These fields are reporting-only: footprint's existing CPU/process verdict and exit code remain unchanged.

The hidden `--cause-only --json` mode performs the `ps` read, answers the capacity question from the spawn-load snapshot, and reads the liveness witnesses attribution needs: the worker claim store, the claude daemon roster, and one bounded liveness probe per unrouted pane row. All of it shares the reading's deadline. It is used by spawn-gate diagnosis, not by the standard closure verdict.

Exit codes are intentionally separate. `0` means the standard closure numbers are within threshold, or that cause-only measurement succeeded. `3` means a standard CPU or direct-process threshold is over budget. `4` means the reading cannot gate: unreadable required input, or a cause-only reading that answers with an attribution gap. Unreadable input covers malformed `ps` rows and incomplete cause evidence. A gapped cause-only reading still prints the measurement, because an undercount is not headroom. An unavailable roster no longer produces exit 4. The process threshold degrades to none, the reason prints beside the reading, and the CPU threshold still applies. A transient direct CLI burst does not produce exit 3 by itself.

Spawn admission decides on fleet-attributed CPU. Load average is what triggers the question. Load average counts runnable and blocked processes together. It measures neither CPU nor anyone's share of it. A box can sit at load 374 while only 54 percent of its CPU is in use. One unscoped recursive search can carry 195 load points alone. Footprint still does not replace load, because a point-in-time CPU snapshot cannot answer whether runnable work is queued.

Both gates read three thresholds. `agents.max_load_per_cpu` times the CPU count is a TRIGGER. Below it a spawn is admitted without probing, so the common path costs no subprocess. Above it the gate asks footprint whose CPU this is. If the fleet holds more than `agents.max_fleet_cpu_share` of capacity, the gate refuses with exit 79. `agents.hard_max_load_per_cpu` times the CPU count is an absolute machine backstop. It refuses whoever caused the load, because a pure fleet-share governor can admit onto a box already thrashing from foreign work. Keep the backstop well above the trigger. The defaults are 8 and 40.

Until this landed the gate decided on load average while printing footprint's contradicting attribution in the same refusal: `1-min load 127.6 exceeds max_load_per_cpu 8 x 12 cpus = 96.0` directly above `footprint attributes 0.79/12.00 cores (6.6% capacity)`. It refused twice on load the fleet did not cause, and on the second occasion it blocked the dispatch of its own repair. A gate that refuses beside its own contradicting measurement teaches an operator to reach for `--force`, which is how a guard becomes a formality.

One divergence between the runtimes is known and open. When attribution is unreadable, both gates refuse. So whichever gives up first refuses first. Python reads in process. Rust runs the same reading as a subprocess. Rust therefore also needs `fno` or `fno-py` to resolve on PATH. In a PATH-stripped context Rust refuses where Python admits, from the same machine state. The timeout half of that gap is closed. The Rust budget is the Python measurement budget plus an allowance for interpreter start. If either number moves, a test fails. The PATH half stays open. To close it, one runtime must call the other's instrument.

The governor and the refusal text read one instrument. The numbers a refusal prints are the numbers it decided on. Unreadable attribution refuses rather than admits. An unknown share is not evidence of headroom. This sensor also goes blind under exactly the load it exists to measure. Missing, timed-out or malformed cause evidence still prints `spawn-gate: footprint cause unavailable; load refusal unchanged` beside the refusal it explains.

This is a human-, CI- or king-invoked reading, not a daemon or poller. A watcher adds the cost being measured.

Mux admission is a separate native pre-spawn instrument. Every Rust child launch except the bootstrap path acquires a per-user machine-global lock. Bootstrap deliberately skips the census, because bootstrap is what recovers a broken gate. It takes a process snapshot without starting an observer. The permit remains alive through the child-creation syscall. The census attributes descendants of active `fno` binaries or the current cargo-test binary and counts OS processes, including live and zombie rows. An ancestry cycle or unreadable required row returns unavailable. The mux root process is not a worker slot.

The process census is compared only with `process_admission.max_processes`, carried by Python as `FNO_PROCESS_ADMISSION_MAX` and defaulting to 400 processes in both runtimes. `agents.max_live` remains an agent count and never enters this channel. Python separately carries the pane-valued `FNO_MUX_PANE_GROUP_MAX`. Every `PanePlacement` carries `max_panes`. A legacy client that omits it receives the conservative configured/default pane cap. Process and pane ceilings remain separate by config key, wire, Rust type and constant.

`measurement-unavailable` is reserved for a failure to read the process table at all. One marker pid nobody can read is not that. On macOS `pid_start_time` and `pid_is_zombie` share one `proc_pidinfo` call. A defunct process therefore reads as no-start-time and not-a-zombie. `kill(pid, 0)` answers EPERM, not ESRCH. Such a pid can never match its recorded start time. It is skipped and pruned from the child ledger. Pruning is also what keeps that ledger bounded. On 2026-09-02 one unreadable entry refused every spawn on the machine.

The recovery switch accepts `on|true|1|yes` and `off|false|0|no`, case-insensitive and trimmed. Its refusal names that set. A switch an operator reaches for while already wedged must not fail closed on a plausible spelling.

Every refusal is a positive, parseable marker: `process admission refused: count=<n> ceiling=<n> scope=<fleet|tab> reason=<over-limit|measurement-unavailable|lock-unavailable>; set FNO_PROCESS_ADMISSION=off to bypass this gate for recovery`. Unknown measurement never becomes count zero or headroom. Bootstrap uses an explicit admission-exempt helper because configuration and the installed CLI can be unavailable during recovery.
## Orphaned cargo test binaries

A wedged cargo test binary never exits and never reaps its children. It sits at 0.0 percent CPU in state `SN` while its dead children stack up as `<defunct>` rows against it. Once the runner that spawned it dies, the binary sits orphaned at ppid 1. Measured instances: 2026-09-01 with 182 zombies, about 3.4 pids per minute. 2026-09-04 with 225 of the machine's 228 zombies after 3h32m. 2026-09-05 with 227 of 228 zombies after 3h07m at ppid 1, 1471 processes, load 203 against a spawn ceiling of 120. The cost is the whole spawn gate. Load average is dominated by process count, so every dispatch on the box refused while sustained CPU read well under threshold.

The detector keys on one invariant. A parentless cargo `deps/` test binary is always wrong: nobody is left to reap it. A deps binary that holds twenty or more `<defunct>` children at any ppid is a wedged reaper, not a running suite. A healthy harness waits its children as tests finish. The parser counts every row whose ppid equals the candidate pid and whose command is exactly `<defunct>`. That string is the real macOS rendering. Confirmation is filesystem work, so it lives in the verb, not the parser. The verb walks up from `deps/` to the owning `target` dir and requires a `CACHEDIR.TAG` file there.

Two traps sit beside this shape. First, never decide from a directory NAME. `cli/src/fno/target`, `skills/target` and `tests/target` are source directories, and a name-based sweep once deleted 66 real cargo target dirs across 26 worktrees in a day. Cargo writes a `CACHEDIR.TAG` into every real target dir, so that file decides, never the path. Second, never kill on an argv pattern. An argv-shaped sweep once signalled 13 live agents that merely shared a launch line. The reaper only ever signals the exact pids the confirmed detector named. A `config.test.orphan_min_elapsed_seconds` guard (default 900) also keeps a possibly live run out of range, because every measured specimen was over three hours old.

The wedged-pair shape is why the zombie clause exists. On 2026-09-06 a deps binary held 81 zombies while its cargo parent was still alive. Cargo had been piped through `tail`. The pipe held after the tests finished, so the parent blocked on a pipe write and never reaped. A ppid-1-only detector misses exactly that measured case. The upstream bounds close the cause: the runner writes suite output to a file, never a pipe, and kills the whole group on expiry.

The lever is `fno-agents orphan-reap`, a binary-direct verb. Dry-run by default, it prints each confirmed orphan with its pid, elapsed time, zombie count and disposition. `--apply` sends SIGKILL to exactly the named pids; `--json` emits the same rows under `orphan_test_binaries`. Detection is native to `fno-agents` (module `orphan_reap`), so the lever answers even when the Python CLI cannot. The daemon runs the same code path with the kill enabled every 300 seconds behind the standard one-in-flight, off-loop sweep gate, and emits an `orphan_test_binary_reaped` event per kill. The box this matters on is the box whose readings go dark.

Two bounds upstream keep the leak from forming in the first place. The suite runner runs each suite in its own process group with a wall-clock timeout (`config.test.timeout_seconds`, default 1800). On expiry or interrupt it kills the GROUP. Killing cargo alone orphans the deps binary it exec'd, which is exactly how the ppid-1 shape forms. And test-spawned children are killed and waited through Drop guards, so a panicking test no longer leaves a live child whose corpse has no reaper.
